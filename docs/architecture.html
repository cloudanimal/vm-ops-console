Vulnerability Management Console · Architecture

Architecture & tech stack

How the console is built: a dependency-light, client-side single-page application that runs entirely in the browser, stores everything locally, and is served as static files from GitHub Pages. This document covers the stack, the module map, the data model, routing, storage, the risk engine, and the planned connector.

Companion to the feature comparison. Reflects the current build.

Design principles

  • Local-first. Imported findings, scan data, notes, settings, and asset tags live in the browser (IndexedDB and localStorage). Nothing is uploaded.
  • No build step. Plain ES5-compatible JavaScript, hand-written CSS, and static HTML. Open the folder in any static server and it runs. No bundler, transpiler, or package install.
  • Dependency-light. A few vendored single-file libraries, each pinned locally; no runtime CDN calls (the strict offline/local posture depends on this).
  • Opt-in egress. Any behavior that would send data off the machine (for example the live EPSS lookup) is off by default, explained, and toggled in Settings.
  • Progressive. A service worker precaches the app shell so it works offline and loads instantly on repeat visits.

Data model

Everything keys off two records, joined by keyOf(f) = CVE + "|" + normalizedHost.

  • Finding { cve, host, severity, cvss, vpr, plugin, name, desc, repo, source, firstSeen, lastSeen, state } — one row per vulnerability-on-host, from an import or a sample source. Stored in vmops-findings.
  • Override { status, owner, notes, repo, updates[], ticket{}, updated } — the user's triage layer, kept separate so re-imports never clobber it. Stored in vmops-overrides.
  • Asset { crit, owner, tags[] } keyed by normalized host — business context that feeds the risk score. Stored in vmops-assets.
  • SBOM { name, at, components[] } — component inventory from an imported CycloneDX BOM (name, version, license, vuln count) for the Licenses & SBOM view. Stored in vmops-sbom.
  • Campaign { id, name, scope, owner, priority, dueDate, status, history[] } — remediation campaigns. Stored in vmops-campaigns.
  • Config — branding, SLA windows, risk weights, ticketing endpoints, nav visibility. Stored in vmops-config. Secrets (API keys) are stored but never exported.

Risk engine

The score is a transparent, user-tunable weighted blend rather than a black box. Each signal contributes raw(0–1) × budget × weight, summed, plus operational pressure (SLA and age).

SignalSourceDefault budget
CVSS / severityFinding CVSS, or severity fallback300
EPSSBundled EPSS feed (opt-in live lookup)300
Exploitation (KEV)CISA KEV / ransomware / public exploit600
LEVNIST LEV local dataset300
SSVCDerived Act / Attend / Track300
Asset criticalityAsset Inventory tier300

Weights (0–2, default 1) are set in Settings; the per-finding drawer shows each signal's exact point contribution. The Remediations view sums these scores per fix to rank "risk removed."

Deployment & the browser boundary

The app deploys as static files to GitHub Pages. Scheduled GitHub Actions rebuild the committed enrichment datasets (KEV, EPSS distribution, LEV, exploited, EOL) so the static data never goes stale. Because it is a pure browser app, six capabilities require the planned connector: live vendor-API pulls, scheduled ingestion, multi-user/RBAC, two-way ticketing, inbound webhooks/CI gating, and notifications. All six collapse to one small self-contained backend that stays on the user's machine or network, keeping the local-first, opt-in posture intact. See the feature comparison for the full boundary analysis.

Security & privacy posture. No account, no telemetry, no third-party hosting of user data. Public CVE lookups are read-only. API keys entered in Settings are stored in this browser only, never uploaded and never included in a settings export. Live EPSS lookup is the only optional egress and is off by default.
